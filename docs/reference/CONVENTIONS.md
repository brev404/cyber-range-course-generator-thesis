# Project Development Conventions

This document outlines the conventions and best practices to be followed by human developers and development assistant agents when building the "Automated System for Cyber Range Content Validation" Master's Dissertation project.

## I. Python Best Practices

The Python codebase for the project will adhere to the following best practices:

1.  **PEP 8 Compliance & Type Hinting:**
    *   Follow the official Python style guide (PEP 8).
    *   Use **Black** for formatting and **Ruff** for linting. Run `black src tests` and `ruff check src tests` before committing. Config in `pyproject.toml`.
    *   **Pre-commit (optional):** `pip install pre-commit && pre-commit install` to run Black and Ruff automatically on commit. See `.pre-commit-config.yaml`.
    *   **Mandatory Type Hinting:** Use Python type hints for all function signatures and class attributes to improve maintainability and enable better IDE support.
    *   Use `snake_case` for function and variable names.
    *   Use `CamelCase` for class names.
    *   Consistent indentation (4 spaces).

2.  **Pydantic V2 for Data Modeling:**
    *   Use Pydantic V2 for all data models (`src/models/`) and configuration management (`src/config/settings.py`).
    *   Leverage Pydantic's validation capabilities to ensure data integrity across agent boundaries.

3.  **Path Management:**
    *   Use the `pathlib` module for all file and directory path operations. Avoid manual string concatenation for paths.

4.  **Clear and Concise Code:**
    *   Write self-documenting code. Use meaningful variable and function names.
    *   Break down large functions into smaller, single-responsibility units.

5.  **Docstrings:**
    *   All modules, classes, and functions must have Google-style docstrings explaining purpose, arguments, and return values.

6.  **Error Handling:**
    *   Implement robust error handling using `try-except` blocks.
    *   Use custom exception classes where appropriate to distinguish between different failure modes (e.g., `ValidationError`, `LLMServiceError`).

7.  **Modularity:**
    *   Maintain the established folder structure.
    *   Minimize inter-module dependencies. Use dependency injection where possible.

8.  **Logging with Loguru:**
    *   Use the `loguru` library for all logging.
    *   Avoid `print()` statements in production code.
    *   Use appropriate log levels: `DEBUG` for development details, `INFO` for general flow, `WARNING` for non-critical issues, and `ERROR` for failures.

9.  **Configuration Management:**
    *   Never hardcode secrets or environment-specific settings.
    *   Use `src/config/settings.py` (Pydantic `BaseSettings`) to load values from `.env`.

## II. LLM Interaction & Agent Orchestration (LangChain/LangGraph)

1.  **Prompt Engineering:**
    *   Keep prompts versioned or clearly defined in the agent classes.
    *   Use structured output (e.g., JSON or Pydantic objects) from LLMs whenever possible to ensure the system can parse the results reliably.

2.  **LangGraph State Management:**
    *   The state in `src/core/state.py` should be treated as the "source of truth" for the workflow.
    *   Ensure state updates are predictable and follow the LangGraph reducer patterns.

3.  **Cost & Token Optimization:**
    *   Be mindful of context window limits. Summarize or truncate data before passing it to the LLM if it exceeds reasonable limits.

## III. Development Assistant Agents: Principles & Guidelines

These guidelines apply to any AI assistant or CLI agent aiding in development.

1.  **Persona: Secure Software Developer:**
    *   Adopt a persona focused on security, robustness, and clean code.
    *   Prioritize the "Cybersecurity Expert Educator" pedagogical goals when writing agent prompts.

2.  **Documentation of Changes:**
    *   Every significant feature or step completion must be documented appropriately (e.g., in a CHANGELOG or commit message).
    *   Update the `README.md` "Current Status" section after completing major phases.

3.  **Roadmap Adherence:**
    *   Development should follow the agreed project plan and track completed steps.

4.  **File Listing Format:**
    *   Always use the strict *file listing* format: Filename on the first line, followed by the code block containing the **entire** file content. Never use ellipses (`...`) to omit code.

5.  **Testing and Running Scripts:**
    *   When testing or running scripts (e.g. pipeline steps, `main.py`, `run_graph`), **use the project virtual environment**. Do not assume it is activated—run with the venv Python path: `./venv/bin/python` (or `./.venv/bin/python` if venv is named `.venv`). Do not assume system Python has the project dependencies.

## IV. Terminology (Course vs writeup)

- **Course** = content generated by this project (one per challenge: generated course text + optional solve script). Use "course" / "generated courses" when referring to this output; state field: `generated_courses`. A course is placed in a module in CyberEDU; a training contains multiple modules.
- **writeup** = author's or participant's solution explained. The existing challenge writeup: the file `writeup.md`, the folder `write-up/`, and any validation or structure checks. Do not rename these; keep "writeup" for file names, validation codes, and challenge structure. See `docs/reference/TERMINOLOGY.md` for full definitions.

## V. Reproducibility (generated courses)

Generated courses must satisfy **reproducibility** (Step 0): (1) Step 0 section with metadata (challenge name, category, difficulty) and documented resources; (2) explicit "what the student has" (description, public files, deployment); (3) "You do NOT have access to" where applicable. See `docs/reference/REPRODUCIBILITY.md` for the full checklist.

## VI. Git & Version Control

1.  **Commit Messages:**
    *   Use [Conventional Commits](https://www.conventionalcommits.org/):
        *   `feat:` for new features.
        *   `fix:` for bug fixes.
        *   `docs:` for documentation changes.
        *   `refactor:` for code changes that neither fix a bug nor add a feature.
    *   Include the git hash in the chat when confirming a commit.

2.  **Atomic Commits:**
    *   Make small, logical commits rather than one giant commit for multiple unrelated changes.
